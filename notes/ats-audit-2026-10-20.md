## 1. Security and access control

### 1.1 `isActive` is not enforced anywhere that matters **[verified]**
- `hasInternalRole` (`src/access/internalRoles.ts:13-22`) and `isCandidateAuthenticated` only check `role`. Every collection access function and every route handler uses them.
- `toggle-active` flips the flag but does not log the user out; Payload login does not consult `isActive`, so a deactivated user can keep using `/admin`, `/api/*` and all form POSTs for the token lifetime (8h internal, 30 days candidate) and can log in again.
- Side effect: inactive users hit a redirect loop (login page redirects to dashboard when a user exists, protected layout redirects back to login when inactive) and never reach the logout button.
- Fix direction: check `isActive` inside `hasInternalRole` / `isCandidateAuthenticated`; add a `beforeLogin` hook rejecting inactive users; call `logoutOperation({ allSessions: true })` from toggle-active; render an "account disabled" page instead of redirecting.

### 1.2 Candidate users can read and edit internal fields **[verified]**
- `candidatesManageAccess` returns a self-row constraint for candidate users and there is no field-level access on any Candidates field. A candidate can PATCH `overallRating`, `technicalSkillsRating`, `applicantStatus`, `notes`, `source`, `sourcedBy`, `resume`, `candidateAccount`, etc.
- `applicationsReadAccess`, `applicationHistoryReadAccess`, `candidateActivitiesReadAccess` all return self rows for candidates with no field filtering: `clientBillRate`, `payRate`, `notes`, `latestComment`, recruiter notes are readable.
- The invite form also pre-fills internal `candidates.notes` into the public form and overwrites it with whatever the candidate submits (`candidate/invite/[token]/page.tsx:229`, `submit/route.ts:228`).
- Fix direction: field-level `read`/`update` access for internal-only fields, or expose a candidate-facing projection instead of the raw collections.

### 1.3 HR collections are writable by any internal user **[verified]**
- `attendanceLogManageAccess`, `leaveRequestManageAccess`, `performanceReviewManageAccess` are all `isInternal`. Hooks never tie `employee` / `reviewer` to `req.user`.
- Consequences: a recruiter can POST an attendance log for a colleague with arbitrary punch times (which writes a `present` daily summary feeding LOP and analytics); create a leave request for anyone; edit dates of an approved leave without re-running the attendance sync; create a performance review with `reviewer` spoofed to an admin and `status: finalized`.
- Fix direction: resolve `employee` from `req.user` for non-admins in `beforeChange`; enforce `reviewer === req.user.id`; freeze non-status fields once a leave is approved; re-run overlap and balance checks on update.

### 1.4 Visibility is global for every internal role **[verified]**
- `clientReadAccess`, `jobsReadAccess`, `applicationsReadAccess`, `candidatesReadAccess` return `true` for admin, lead and recruiter. The scoped selectors in `src/lib/assignments/selectors.ts` are used only by the RecruiterJobAssignments hook, never by pages or access.
- A recruiter sees every client (including contact, billing terms, federal ID, notes), every job, every candidate, every application, and can move any application on any job (`applicationsUpdateAccess` is a plain role check).
- UI copy contradicts itself: route is `/jobs/assigned`, modal says "your current visibility scope", nav description says recruiters "view all jobs across the workspace".
- Decision needed: either make the selectors the source of truth inside the access functions (as `Where` constraints) or drop the "assigned/scope" wording and selectors.

### 1.5 Media collection
- Only `read: () => true` is defined, so create/update/delete fall back to "any authenticated user", including candidate accounts. SVG uploads are allowed and served same-origin when S3 is off (stored XSS). Candidates can delete client logos.
- Fix: internal-only create/update/delete; drop `image/svg+xml` or serve as attachment.

### 1.6 Other security items
- `/api/jobs/reactivate/:id` spreads the raw request body into the update (`src/collections/Jobs.ts:170-188`): a lead can overwrite `client`, `owningHeadRecruiter`, `createdBy`, `jobCode`. Neither this nor the JobRequests process endpoint is called from the UI.
- Lead recruiters can change any recruiter's email/password via `PATCH /api/users/:id` (`Users.ts:33-49`). Role escalation is correctly blocked.
- `JobLeadAssignments` trusts `client` from input instead of deriving it from the job; a mismatched row grants a lead visibility of an unrelated client.
- `src/lib/auth/payload-auth-headers.ts:41-76` strips `Origin` and forges `Sec-Fetch-Site: same-origin` to work around a stale `APP_URLS`. Set `APP_URLS` correctly in Vercel and delete the shim.
- Both auth collections share the `payload-token` cookie name, so logging into one portal logs the browser out of the other. Add `cookies.prefix` on CandidateUsers.
- Logout routes are plain POSTs that work without a session (cross-site logout CSRF, low).
- No security headers at all in `next.config.mjs` (no CSP, frame-ancestors, referrer policy). `cors`/`csrf` always include `http://localhost:3000` in production.
- Raw `error.message` from Payload/Drizzle is reflected into `?error=` on most handlers (leaks constraint names and internals; invite route leaks the Resend placeholder message to the public).
- `candidate.linkedInURL` / `portfolioURL` are rendered straight into `href` (`P/candidates/[id]/page.tsx:674,679`) with no protocol allow-list; URLs come from the LLM parser or user input.
- CSV export (`BulkTableControls.tsx:11-29`) does not escape leading `=`, `+`, `-`, `@` (Excel formula injection via parsed resume text). The analytics Excel export does escape correctly.
- Candidate direct-create route (`P/candidates/create/route.ts:245`) has no size limit and trusts the browser MIME type; the two other upload routes enforce 10MB.
- Leftovers to delete: `src/app/my-route/route.ts` (unauthenticated template route), `sendHelloWorldEmail` with a hard-coded personal address in `src/lib/email/resend.ts`, "Remember this device" no-op checkbox, "Forgot Password?" linking to `/`.

## 2. Candidate portal and invites

### 2.1 Invite flow is dead code **[verified]**
- `generateCandidateInviteToken`, `sendCandidateInviteEmail`, `buildCandidateInviteLink` have zero callers. No code creates a `candidate-invites` doc; the only references are the token lookup and the consume step.
- `CandidateInvites.beforeValidate` throws without `tokenHash` and the field is hidden, so invites cannot be created from `/admin` either.
- `Applications.ts:560` stamps `candidateInvitedAt` on L1-scheduled but dispatches nothing. The "Invite to Job" button on the candidate detail page just links to the new-application form. README "Phase 6" describes behaviour that no longer exists.
- Decision: wire an "Invite candidate" action (create invite + send email, probably in the Applications stage hook) or remove the portal, `candidate-users`, and invite code.

### 2.2 Invite submit route (latent until 2.1 is fixed) **[verified]**
- Five separate writes with no `req`/transaction; if the email step throws (Resend key unset) the account and stage change are committed but the invite stays `pending`, and the raw config error is shown to the candidate.
- Resend's `send()` returns `{ error }` and does not throw; the result is ignored, so real delivery failures are swallowed and `accountAccessSentAt` is still set. Default `from: onboarding@resend.dev` only delivers to the Resend account owner.
- Uses the submitted `email` instead of `invite.inviteEmail` (an invite holder can bind the account to someone else's email, and the error message is an "is this email registered" oracle). Existing accounts get `isActive: true` forced back on.
- All redirects are 307 (re-POSTs the form including the password) instead of 303.
- Email links are built from raw `process.env.NEXT_PUBLIC_APP_URL` (`resend.ts:29`) rather than `env.NEXT_PUBLIC_APP_URL`, so on Vercel without that var every link points to localhost.
- Email HTML interpolates `candidateName`/`jobTitle` unescaped.

### 2.3 Portal pages
- Candidate dashboard and applications pages show job IDs instead of titles: `jobsReadAccess` returns false for candidates so Payload populates bare IDs (`candidate/(protected)/dashboard/page.tsx:68`, `applications/page.tsx:20-22`). Same for recruiter.
- Portal still uses the legacy dark `internal-shell` layout and reuses `kanban-*` classes for a profile card; internal uses `ops-shell`.
- No `error.tsx`, `not-found.tsx` or `loading.tsx` for the candidate segment.

## 3. Candidates and resume import

### 3.1 Bulk import **[verified]**
- Retry / "Continue Processing" path fetches the stored resume via an unauthenticated HTTP call to the app's own file endpoint (`resume-imports.ts:197-202`); the endpoint enforces read access, so with S3 off every retry fails with 401/403. Only the in-memory buffer path from the create route works.
- Processing is not idempotent: items are selected by `status in ['queued']` and flipped to `processing` one at a time with no claim. Clicking "Continue Processing" while the `after()` job is still running parses the same items twice (double Ollama cost, clobbered stats).
- No `maxDuration` exported anywhere and `ollama.chat` has no timeout; Vercel kills the function mid-loop, items sit in `processing` for 10 minutes, and the batch page does not auto-refresh.
- The process route re-queues any item id regardless of status, including `candidateCreated`; `findByID` is not try/caught so a bogus id 500s.
- Vercel's request body limit (~4.5MB) means the advertised 5 × 10MB upload cannot work in prod; worth checking the plan limit.
- `.doc` files are accepted everywhere but `extractResumeText` returns empty for them.
- LLM failures (missing key, 401, bad JSON) are swallowed into a warning string and saved as `needsReview` with heuristic data; the UI only offers Retry for `failed` items and gives no "fallback only" indication.
- Prompt-injection surface: resume text goes into the user turn; the JSON schema constrains shape but values (`notes`, `skills`, URLs) are auto-applied to the form and saved verbatim.

### 3.2 Candidate record **[verified]**
- `getCandidateSignals` and the `beforeChange` return use `data.x ?? originalDoc.x`, so sending `null` can never unlink `resume`, `sourceJob`, `sourcedBy`. Clearing `email` to null leaves `normalizedEmail` set to the old value, so the unique index keeps rejecting any other candidate with that email with no visible owner.
- Edit route maps every empty input to `undefined` so nothing except the two checkboxes can be cleared from the Edit screen.
- Recruiters can edit any candidate by POSTing to the create route with `candidateId` even though the Edit page and buttons are hidden for them (`candidatesManageAccess` grants recruiters update on every candidate). Decide which is intended.
- Phone dedupe strips non-digits only: `+91 98765 43210` and `98765 43210` are different keys. Normalize to E.164 with a default country code.
- Dedupe and `candidateCode` generation are find-then-insert with no retry; concurrent creates surface as raw Postgres unique-violation text instead of the 409.
- Candidates list caps at 240 candidates / 600 applications then searches, filters and paginates in JS; "Showing X of Y" is wrong past the cap.
- Replacing a resume on Edit orphans the previous `candidate-resumes` doc.
- Detail/edit/batch pages `catch { notFound() }`, turning DB errors into 404s.

## 4. Jobs, clients, assignments, dashboard

### 4.1 Functional dead-ends **[verified]**
- Lead-created job gets `owningHeadRecruiter = lead` but no `job-lead-assignments` row (only created for admins, `P/jobs/create/route.ts:335`). `RecruiterJobAssignments` then rejects the lead with "can only assign recruiters to jobs explicitly assigned to them". The lead assignment page lists all jobs in the dropdown, so the lead picks their own job and gets a 403.
- Sidebar "+ Post New Job" and dashboard "Post Job" link to `/internal/jobs/assigned#create-job`; the modal only opens on `?create=1` and nothing handles the hash. The button does nothing (and is shown to recruiters who cannot create).
- Admin nav has no entry for `/internal/assignments/head`; `/internal/jobs/templates` is in no nav at all. "Export Data" on the jobs page links to the applications list.

### 4.2 Data integrity
- Jobs list has a mandatory 30-day (max 90) `updatedAt` window plus `limit: 120, pagination: false`; jobs untouched for 90 days are unreachable from the UI. Client cards link into that window, so "3 active" on the card can show "No jobs found".
- Job detail shows `applications.totalDocs` as "N Applicants" but with `pagination: false` that equals the capped row count (220).
- Assignment desks compute "unassigned" clients/jobs as entities minus the first 120 assignment rows sorted by recency; past 120 rows, old active assignments fall off, the admin re-assigns, and the dedupe hook rejects with "already has an active assignment".
- Job status transitions are unvalidated: closing a job with open applications/interviews does nothing to them; `JobRequests` reactivation spreads intake data over the historical job wholesale.
- Multiple active lead assignments per job/client are possible; `owningHeadRecruiter` is last-writer-wins and sibling rows are never deactivated.
- Client lead cannot be unassigned: `owningHeadRecruiter: null ?? original` resurrects the old lead, so "Unassigned" is a no-op.
- Jobs/clients edit routes map empty inputs to `undefined` (cannot clear department, location, salary, dates, website, etc.); replacing a JD or logo orphans the old media doc.
- Assignment dedupe is read-then-write with no partial unique index.
- Multi-step route handlers (create job → create assignment, create assignment → update owner, process job request) are not transactional.

### 4.3 Dashboard
- Velocity chart mixes local-midnight day keys with UTC bucket keys; on a non-UTC server every bar shifts one day.
- Lead "Pending Reviews" KPI is `length` of a `limit: 6` query, so it can never exceed 6; "avg wait" is over those 6.
- Approval rate counts `toStage: 'sourced'` (new submissions and send-backs) as reviewed.
- Admin "Leads Assigned" sums client rows plus job rows (same lead counted repeatedly).
- Hard-coded fake deltas ("+12%", "-2%", "Client Meeting in 2h", `+{round(pending/2)} this week`). Recruiter Load "% capacity" is share-of-max, not capacity.
- Unreachable placeholder branch after the lead/recruiter branches.

### 4.4 Debug leftovers **[verified]**
- `P/jobs/assigned/[id]/page.tsx:470` has `console.log({member, index})` inside the JSX map (runs on every server render); the initials code is commented out and the full name is printed in a 2-char avatar pill.

## 5. Applications, interviews, placements, schedule

### 5.1 Interview → application stage hook **[verified]**
- `Interviews.afterChange` runs on every update and sets `applications.stage = stageFromInterviewStatus(status, round)` from the interview round alone, without `skipStageTransitionValidation`, so `validateStageTransition` runs with the real user's transition table.
  - App at `l3Scheduled`; recruiter marks the earlier screening interview completed → target `l2Scheduled` → 403 and the interview save fails.
  - Same action as admin → application silently regresses `l3Scheduled → l2Scheduled`, bogus history row, `interviewAt` overwritten with the old start time.
  - Creating an interview with `status=completed` jumps stages.
- `Placements.afterChange` has the same shape: every edit rewrites `latestComment`/`placedAt`; cancelling never reverts.
- Fix: transition only on create or status change, compute target relative to the current stage (never backward), run as a system action with the real actor recorded in history.

### 5.2 Time handling **[verified]**
- Interview form posts `datetime-local` (no offset); the route does `new Date(raw).toISOString()` in the server zone. 10:00 IST entered → stored 10:00 UTC → shown 15:30 IST. The `timezone` field (default Asia/Kolkata) is stored but never used.
- Schedule page: oldest 350 interviews only (ascending sort), "Upcoming Sessions" shows the 24 oldest, day keys use local-midnight-to-UTC, "Your Capacity" counts everyone's interviews ÷ 10. No `timeZone` passed to any `toLocale*` call anywhere in the repo.

### 5.3 Other pipeline items
- Review queue: ascending `updatedAt` with `limit: 220`, then default 7-day window in memory; past 220 pending, the newest are cut and the oldest hidden by default.
- Kanban board (`JobApplicantsBoard.tsx`): rollback restores a whole pre-move snapshot (reverts other cards' persisted moves), no refetch on success, fabricated history entry hardcodes actor as the recruiter, server returns 400 for every error including 403.
- Placement form offers applications that already have a placement on another page; submit then shows the raw unique-index error.
- No interview double-booking check for candidate or interviewer.
- Rejection is terminal for non-admins but admins and the hooks above can pull a rejected application back; unique `(candidate, job)` means a rejected candidate can never be re-sourced for that job without admin help.
- `catch { notFound() }` on application and job detail pages hides DB/hook errors.

## 6. HR (attendance, leave, performance, analytics, team settings)

### 6.1 Timezone **[verified]**
- `lateMinutes` compares `inDate.getHours()` (UTC on Vercel) against the IST shift start: 14:00 IST punch reports 0 late, 16:00 IST reports 45 min.
- Daily summary date keys use `setHours(0,0,0,0)`/`toDateOnly` in server zone; punches between 00:00–05:29 IST file under the previous day. Same helpers in leave, performance, analytics, attendance-query behave differently locally vs prod, so summaries created in each environment disagree on the `[employee, date]` key.
- Attendance page formats on the server (UTC) while the punch widget formats in the browser (IST): the same punch shows two different times on one screen. Locale is mixed en-IN / en-US / bare.

### 6.2 Leave accounting **[verified]**
- `accrued = accrualPerMonth * 12` AND `openingBalance = annualAllowance` → CL/SL show 24 instead of 12. Balances are created lazily on first approval, so the page shows "No leave balances" until then.
- No balance check on apply or approve; nothing ever restores `used`; a Dec→Jan leave is charged entirely to the start year; `upsertLeaveBalance` is find-then-update (concurrent approvals lose increments).
- Day count is pure calendar days; the attendance sync overwrites weekOff/holiday summaries with `leave` for every day in range. Fri–Mon costs 4 days. `maxConsecutiveDays`, `minUnit`, `isActive` on leave types are never enforced.
- Admins can approve their own leave (via REST); `leadApprover`/`reportingManager` is set but never enforced, so any lead approves any recruiter.

### 6.3 Attendance
- Punch-in race: find-open-session then create with no constraint or transaction; two concurrent requests create two open logs and punch-out closes only the latest, leaving an orphan "Currently Punched In" forever. No auto-close for forgotten punch-outs (multi-day `workedMinutes`).
- `AttendanceShifts.isDefault` and shift `weeklyOffDays` are never consumed; profiles without a shift never get late marks. Shift time regex accepts "99:99".
- Analytics attendance % only counts days with a summary row; no row is ever written for absent days, so 1 punch in 22 days = 100%.

### 6.4 Performance and analytics
- Snapshot window uses `less_than_equal: midnight of endDate`, dropping the last day of the cycle. Snapshots only for `isPayrollEligible` employees. `avgTurnaroundHours: 24` and `slaBreachesCount: 0` are placeholders; cycle `status` is never enforced.
- Analytics caps (`limit: 3000` summaries/applications, 2000 leave, 5000 history) silently truncate at 20 employees × 180 days.
- Leave page `limit: 120` newest then filters by period; older pending requests vanish from approval queues. Performance page same with 200.

### 6.5 Team settings **[verified]**
- Admin can deactivate themselves or the last admin (`toggle-active/route.ts:39-47`, no checks) → lockout with no UI recovery.
- Password length is enforced client-side only.

## 7. Platform, ops, tests

- **Email:** no Payload `email` adapter configured, so admin forgot-password and verification are console-only; SMTP_* env vars are read nowhere; "Forgot Password?" links to `/`. **[verified]**
- **Uploads without S3:** `S3_UPLOADS_ENABLED` is derived from four vars; when any is missing, uploads go to `media/` on disk, which is read-only on Vercel. No production warning. **[verified]**
- **Serverless DB pool:** `max: DATABASE_POOL_MAX || 5` per lambda instance; with concurrent cold starts this can exceed a small Aiven/Neon connection limit. Set `DATABASE_POOL_MAX=1` or `2` on Vercel or use a pooler.
- **Preview deployments** now run `payload migrate` via `vercel.json` against whatever `DATABASE_URL` the preview environment has; if previews share the prod DB, a PR migration mutates prod before merge. The env vars are set for Preview and Production, so this is the case today. Consider scoping `DATABASE_URL` for Preview to a separate DB.
- **Tests:** no CI at all. `tests/e2e/frontend.e2e.spec.ts` asserts the Payload template title and heading, so it always fails. `tests/helpers/seedUser.ts` deletes `admin@ats.com` against whatever `DATABASE_URL` is in `.env` (dangerous with prod creds). `api.int.spec.ts` boots Payload under jsdom. Playwright uses `pnpm dev` while the repo uses npm. The 12 passing unit tests only cover pure helpers; none of the bugs above would fail them. **[verified: suite passes on a fresh DB]**
- **Docker:** Dockerfile copies `.next/standalone` but `output: 'standalone'` is not set; docker-compose uses node 18 and depends on mongo while the app uses Postgres.
- **Migrations:** parsed generated schema vs. migration SQL: no further drift beyond `clients.created_by_id` (fixed today). Only the init migration has a Drizzle JSON snapshot, so `migrate:create` diffs are unreliable; keep hand-writing migrations.
- **Misc:** `.gitignore` now has `.env*` which also matches the tracked `.env.example`; stale `.yarnrc`; `test.env` unused; `@payloadcms/storage-s3` is caret-ranged while every other Payload package is pinned; GraphQL endpoint is on by default with no need for it.
- **Local dev note:** today's `vercel env pull` overwrote `.env` and `.env.local` with `[SENSITIVE]` placeholders; local values must be restored before localhost works.

## 9. Ideas backlog (improvements, not bugs)

**Architecture**
- One `toBusinessDate(date, 'Asia/Kolkata')` helper (or a `timezone` on EmployeeProfile) used by punches, lateness, leave expansion, holiday matching, analytics, schedule, dashboard; one `formatDate/formatDateTime` helper with explicit `timeZone` and `en-IN` for all ~30 call sites.
- A single pipeline service for application stage changes (interviews, placements, board, review) that knows the current stage, never moves backward, runs as a system actor, and records the real actor.
- Server-side pagination and `where` filters on every list page (clients and templates already do it); `payload.count` for KPIs; "all time" option on jobs.
- Partial unique indexes: active assignments `(job, recruiter) WHERE status='active'`, open attendance logs `(employee) WHERE punch_out_at IS NULL`, and wrap punch-in / assignment creation in transactions.
- Make edit routes distinguish "absent" from "cleared" (send `null`), and delete replaced media/resume docs.
- Move bulk resume processing to a Payload job/queue with one item per invocation, atomic claim (`update where status='queued'`), `maxDuration`, `AbortSignal.timeout` on Ollama, and batch page auto-refresh.
- Nightly job: auto-close stale punch-ins, write `absent` summaries for working days with no activity, accrue leave balances monthly.

**Product**
